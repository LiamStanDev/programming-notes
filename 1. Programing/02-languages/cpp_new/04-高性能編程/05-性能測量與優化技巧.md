# 性能測量與優化技巧 (Performance Measurement & Optimization)

## 1. 核心原則

**"You can't optimize what you can't measure."**

在 HFT 和高性能計算中，直覺往往是錯誤的。必須依賴精確的測量數據來指導優化。

### 1.1 優化循環 (The Optimization Loop)
1.  **Measure (測量)**: 建立基準 (Baseline)。
2.  **Profile (分析)**: 找出熱點 (Hotspots) 和瓶頸。
3.  **Optimize (優化)**: 應用優化技術。
4.  **Verify (驗證)**: 再次測量，確認改進且無副作用。

---

## 2. 微基準測試 (Micro-benchmarking)

微基準測試用於測量小段代碼的性能。

### 2.1 Google Benchmark
業界標準的 C++ Benchmark 庫。

```cpp
#include <benchmark/benchmark.h>
#include <vector>
#include <numeric>

// 測試目標函數
static void BM_VectorAccumulate(benchmark::State& state) {
    // Setup (不計入時間)
    std::vector<int> v(state.range(0), 1);
    
    // 測試循環
    for (auto _ : state) {
        // 核心邏輯
        int sum = std::accumulate(v.begin(), v.end(), 0);
        
        // 防止編譯器優化掉結果
        benchmark::DoNotOptimize(sum);
    }
    // Teardown (自動)
}

// 註冊測試，參數範圍 8 到 8k
BENCHMARK(BM_VectorAccumulate)->Range(8, 8<<10);

BENCHMARK_MAIN();
```

### 2.2 常見陷阱
1.  **編譯器優化**: 如果結果未被使用，編譯器可能刪除整個計算過程。使用 `benchmark::DoNotOptimize()`。
2.  **冷啟動 vs 熱運行**: CPU Cache 和分支預測器需要預熱。Benchmark 庫通常會自動處理，但在手寫測試時要注意。
3.  **系統干擾**: OS 調度、電源管理 (CPU 降頻) 會影響結果。應在隔離環境或設置 CPU 為 Performance 模式下運行。

## 3. 延遲測量 (Latency Measurement)

對於 HFT，**延遲分佈 (Latency Distribution)** 比平均延遲更重要。關注 P99 (99th percentile) 和 Max Latency。

### 3.1 高精度計時

```cpp
#include <chrono>

// 使用 steady_clock 保證單調遞增
using Clock = std::chrono::steady_clock;

void measure_latency() {
    auto start = Clock::now();
    
    // 執行關鍵操作...
    do_critical_work();
    
    auto end = Clock::now();
    auto nanos = std::chrono::duration_cast<std::chrono::nanoseconds>(end - start).count();
    
    record_latency(nanos);
}
```

### 3.2 CPU 週期計數 (RDTSC)
在極低延遲場景 (< 1us)，`std::chrono` 可能有開銷。可以使用 CPU 指令 `rdtsc` 讀取時間戳計數器。

```cpp
#include <x86intrin.h>

inline uint64_t rdtsc() {
    return __rdtsc();
}

// 注意: 需要測量 CPU 頻率來轉換為納秒，且需確保線程不遷移 (CPU Affinity)
```

### 3.3 延遲直方圖 (Histogram)
不要只記錄平均值。使用直方圖記錄所有樣本。

```cpp
class LatencyRecorder {
    std::vector<uint64_t> samples_;
public:
    void record(uint64_t ns) { samples_.push_back(ns); }
    
    void print_stats() {
        std::sort(samples_.begin(), samples_.end());
        size_t n = samples_.size();
        std::cout << "Avg: " << calculate_avg() << " ns\n";
        std::cout << "P50: " << samples_[n * 0.50] << " ns\n";
        std::cout << "P99: " << samples_[n * 0.99] << " ns\n";
        std::cout << "Max: " << samples_.back() << " ns\n";
    }
};
```

## 4. 性能分析工具 (Profiling Tools)

### 4.1 Linux Perf
強大的系統級分析工具，利用 CPU 硬件計數器。

```bash
# 1. 概覽 (Cache misses, Branch misses, Instructions per cycle)
perf stat -d ./app

# 2. 採樣熱點 (Sampling)
perf record -g ./app
# 查看報告
perf report

# 3. 火焰圖 (FlameGraph) 可視化
# perf script | ./stackcollapse-perf.pl | ./flamegraph.pl > perf.svg
```

### 4.2 Valgrind (Cachegrind / Callgrind)
模擬 CPU 執行，提供精確的 Cache 行為分析，但速度極慢 (50x 減速)。

```bash
# 分析 Cache Misses
valgrind --tool=cachegrind ./app

# 分析函數調用圖
valgrind --tool=callgrind ./app
# 使用 kcachegrind 查看可視化結果
```

## 5. 優化技巧總結

### 5.1 代碼層面
*   **數據結構**: 優先 `std::vector`/`std::array`，避免 `std::list`/`std::map`。
*   **分支**: 消除熱路徑上的不可預測分支，使用 `[[likely]]`。
*   **內存**: 減少動態分配 (malloc/free)，使用內存池 (Memory Pool)。
*   **虛函數**: 避免熱路徑上的虛函數調用，使用 CRTP 或 `std::variant`。

### 5.2 編譯層面
*   **優化級別**: `-O3`。
*   **架構特定**: `-march=native`。
*   **LTO**: `-flto` (鏈接時優化)。
*   **PGO**: Profile-Guided Optimization (兩階段編譯)。

### 5.3 系統層面 (HFT 特定)
*   **CPU 隔離 (Isolcpus)**: 將關鍵線程綁定到專屬核心，避免 OS 調度干擾。
*   **Kernel Bypass**: 使用 Solarflare OpenOnload 或 DPDK 跳過內核網絡棧。
*   **預熱 (Warm-up)**: 在開市前預運行代碼，填充 Instruction Cache 和 TLB。

---

## 6. 實戰檢查清單

1.  **基準建立**: 優化前先記錄 Baseline 性能。
2.  **熱點定位**: 使用 `perf` 確認瓶頸在哪裡 (CPU? Cache? I/O?)。
3.  **逐步優化**: 一次只做一個改動，並驗證效果。
4.  **關注 P99**: 解決長尾延遲 (Tail Latency) 往往比提升平均值更難也更重要。
5.  **代碼可讀性**: 不要在非熱點路徑上進行過度優化 (Premature Optimization)。
