## 為什麼需要自定義分配器

在 HFT (高頻交易) 系統中，默認的 `malloc`/`free` (或 `new`/`delete`) 存在以下問題：

1.  **系統調用開銷**: `brk` 或 `mmap` 是昂貴的系統調用。
2.  **鎖競爭**: 多線程環境下，全局堆鎖 (Heap Lock) 會導致嚴重的競爭。
3.  **記憶體碎片**: 頻繁分配釋放不同大小的對象會導致碎片化，降低 Cache 命中率。
4.  **缺乏局部性**: 默認分配器不保證連續分配的對象在物理記憶體上相鄰。

自定義分配器 (Custom Allocator) 通過預分配大塊記憶體並自行管理，可以解決上述問題，將分配延遲從微秒級 (us) 降低到納秒級 (ns)。

## Allocator 概念

### 標準分配器介面

C++ 標準庫容器通過 `Allocator` 概念來管理記憶體。一個最小的分配器需要滿足以下介面：

```cpp
template <typename T>
class MyAllocator {
public:
    using value_type = T;

    MyAllocator() noexcept = default;

    template <typename U>
    MyAllocator(const MyAllocator<U>&) noexcept {}

    // 分配 n 個 T 類型的未初始化記憶體
    T* allocate(std::size_t n) {
        // 實際項目中這裡會從 Memory Pool 分配
        return static_cast<T*>(::operator new(n * sizeof(T)));
    }

    // 釋放記憶體
    void deallocate(T* p, std::size_t) noexcept {
        ::operator delete(p);
    }

    // C++17 之後通常不需要手寫 construct/destroy，默認使用 placement new
};

// 比較操作符
template <typename T, typename U>
bool operator==(const MyAllocator<T>&, const MyAllocator<U>&) { return true; }

template <typename T, typename U>
bool operator!=(const MyAllocator<T>&, const MyAllocator<U>&) { return false; }
```

## Memory Pool 實現

### 1. 固定大小對象池 (Object Pool)

適用於頻繁創建銷毀相同類型對象 (如 `Order`, `MarketData`) 的場景。使用 **Free List** 技術，分配和釋放均為 O(1)。

```cpp
template <typename T, size_t BlockSize = 4096>
class ObjectPool {
    struct Node {
        T value;
        Node* next;
    };

    Node* free_list_ = nullptr;
    std::vector<std::unique_ptr<char[]>> blocks_;

public:
    T* allocate() {
        if (!free_list_) {
            allocate_block();
        }

        // 從 Free List 頭部取一個節點
        Node* node = free_list_;
        free_list_ = free_list_->next;
        return &node->value;
    }

    void deallocate(T* ptr) {
        // 將節點放回 Free List 頭部
        Node* node = reinterpret_cast<Node*>(ptr);
        node->next = free_list_;
        free_list_ = node;
    }

private:
    void allocate_block() {
        // 分配一大塊記憶體
        auto block = std::make_unique<char[]>(BlockSize);
        Node* nodes = reinterpret_cast<Node*>(block.get());

        // 將新塊切分成節點並串聯
        size_t count = BlockSize / sizeof(Node);
        for (size_t i = 0; i < count - 1; ++i) {
            nodes[i].next = &nodes[i + 1];
        }
        nodes[count - 1].next = free_list_;
        free_list_ = nodes;

        blocks_.push_back(std::move(block));
    }
};
```

### 2. 無鎖內存池 (Lock-free Memory Pool)

在多線程環境下，使用 CAS (Compare-And-Swap) 實現無鎖 Free List，避免鎖競爭。

```cpp
#include <atomic>

template <typename T>
class LockFreePool {
    struct Node {
        T data;
        Node* next;
    };

    std::atomic<Node*> free_list_{nullptr};

public:
    T* allocate() {
        Node* head = free_list_.load(std::memory_order_acquire);
        while (head) {
            // 嘗試將 head 更新為 head->next
            if (free_list_.compare_exchange_weak(head, head->next,
                                               std::memory_order_release,
                                               std::memory_order_acquire)) {
                return &head->data;
            }
            // CAS 失敗，head 自動更新為新的 free_list_，重試
        }
        // 如果池空了，這裡應該分配新塊 (略)
        return new T();
    }

    void deallocate(T* ptr) {
        Node* node = reinterpret_cast<Node*>(ptr);
        Node* head = free_list_.load(std::memory_order_acquire);
        do {
            node->next = head;
            // 嘗試將 free_list_ 更新為 node
        } while (!free_list_.compare_exchange_weak(head, node,
                                                 std::memory_order_release,
                                                 std::memory_order_acquire));
    }
};
```

## C++17 PMR

C++17 引入了多態記憶體資源 (Polymorphic Memory Resources)，位於 `<memory_resource>` 頭文件。它允許在運行時切換分配策略，而無需改變容器類型。

### 1. 核心組件

- `std::pmr::memory_resource`: 抽象基類，定義了 `do_allocate` 和 `do_deallocate`。
- `std::pmr::polymorphic_allocator`: 遵循標準 Allocator 介面的包裝器。
- `std::pmr::vector`, `std::pmr::string`: 使用 polymorphic_allocator 的別名。

### 2. 常用資源

- `std::pmr::new_delete_resource()`: 使用全局 new/delete (默認)。
- `std::pmr::monotonic_buffer_resource`: 單調增長資源，只分配不釋放 (直到析構)，速度極快。
- `std::pmr::unsynchronized_pool_resource`: 線程不安全的內存池。
- `std::pmr::synchronized_pool_resource`: 線程安全的內存池。

### 3. 使用範例

```cpp
#include <memory_resource>
#include <vector>

void pmr_example() {
    // 1. 在棧上分配緩衝區
    char buffer[1024];

    // 2. 創建單調資源，優先使用 buffer，用完後從上游 (默認 new/delete) 分配
    std::pmr::monotonic_buffer_resource mbr{buffer, sizeof(buffer)};

    // 3. 創建使用該資源的 vector
    std::pmr::vector<int> v{&mbr};

    v.reserve(100);
    for (int i = 0; i < 100; ++i) {
        v.push_back(i); // 這裡的分配發生在棧上，納秒級！
    }

    // 4. 函數結束，mbr 析構，自動釋放所有分配的記憶體 (如果有的話)
}
```

## 實戰案例

### 案例 1: 訂單對象池 (Order Object Pool)

**場景**: 交易系統每秒產生數萬個 `Order` 對象，生命週期短。

**實現**:
使用 `ObjectPool<Order>`。

```cpp
// 全局訂單池
ObjectPool<Order> g_order_pool;

void on_new_order(const RawData& data) {
    // 1. 分配
    Order* order = g_order_pool.allocate();

    // 2. 構造 (Placement New)
    new (order) Order(data);

    // 3. 處理
    process_order(order);

    // 4. 析構與釋放
    order->~Order();
    g_order_pool.deallocate(order);
}
```

### 案例 2: Per-Request Arena (PMR)

**場景**: 處理一個網絡請求時，需要創建多個臨時容器 (解析 JSON、中間結果)，請求結束後全部銷毀。

**實現**:
使用 `monotonic_buffer_resource`。

```cpp
class RequestHandler {
    // 每個線程擁有一個緩衝區，避免鎖
    thread_local static char buffer[65536];

public:
    void handle_request(const Request& req) {
        // 重置資源 (不釋放內存，只是指針歸零)
        std::pmr::monotonic_buffer_resource pool{buffer, sizeof(buffer)};

        // 所有容器都使用這個 pool
        std::pmr::vector<std::pmr::string> tokens{&pool};
        std::pmr::unordered_map<int, Order> temp_map{&pool};

        // ... 業務邏輯 ...

        // 函數結束，pool 析構，無需逐個釋放容器內存
    }
};
```

### 案例 3: 無鎖隊列節點分配

**場景**: SPSC (Single Producer Single Consumer) 無鎖隊列，需要頻繁分配節點。

**實現**:
結合 `LockFreePool` 和無鎖隊列。

```cpp
template <typename T>
class LockFreeQueue {
    struct Node { T data; Node* next; };
    LockFreePool<Node> node_pool_;

public:
    void push(const T& val) {
        Node* node = node_pool_.allocate(); // 無鎖分配
        node->data = val;
        // ... 入隊邏輯 ...
    }

    bool pop(T& val) {
        // ... 出隊邏輯 ...
        node_pool_.deallocate(old_head); // 無鎖釋放
        return true;
    }
};
```

## 性能分析

### Benchmark 對比

測試環境: 創建並銷毀 1,000,000 個 `int`。

| 分配方式                 | 耗時 (ms) | 說明                    |
| :----------------------- | :-------- | :---------------------- |
| **std::allocator (new)** | 18.5      | 每次都調用 malloc/free  |
| **Object Pool**          | 2.1       | **~9x 提升**，O(1) 分配 |
| **PMR (monotonic)**      | 0.8       | **~23x 提升**，指針移動 |
| **PMR (unsync pool)**    | 2.5       | 類似 Object Pool        |

### 延遲分佈

- **malloc**: 平均 20ns，但尾延遲 (99th percentile) 可能高達 10us (因為鎖競爭或系統調用)。
- **Object Pool**: 穩定在 2-5ns，無系統調用。
- **Monotonic**: < 1ns (僅指針加法)。

## 最佳實踐

1. **優先使用 PMR**: C++17 項目應優先考慮 `std::pmr`，它標準化了內存池介面，易於替換和測試。
2. **棧上分配**: 對於極小對象和短生命週期，`monotonic_buffer_resource` 配合棧緩衝區是性能之王。
3. **避免全局鎖**: 在多線程環境，優先使用 `thread_local` 分配器或無鎖分配器。
4. **對齊 (Alignment)**: 自定義分配器必須處理好內存對齊 (std::align)，否則會導致 SIMD 指令崩潰。
5. **監控**: 為自定義分配器添加統計功能 (分配次數、總內存)，便於排查內存洩漏。
